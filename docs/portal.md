# Customer self-service billing portal (`apps/portal`)

A customer-facing Next.js app where the **end-users of any opted-in Application** sign in and manage their own subscription — without the operator building any billing UI or running their own service.

## Portal V2 — hosted, multi-app (current)

One Rekey-hosted portal serves **every** opted-in Application, resolved by the `<slug>` in the URL: `portal.rekey.dev/<slug>`. The operator turns it on per-Application in **Panel → Application → Billing → Portal** and gets the URL — no deploy, no secret key.

**Credential model.** The portal holds **no per-app secret key**. It looks up each app's public config (`GET /api/v1/portal/config/:slug` → name + **publishable key** + branding) and authorizes each customer with **their own session token**. The self-service billing routes (`subscription`, `entitlements`, `payments`, `cancel`, `checkout`) accept the publishable key + the caller's token and act only on that caller's own resources. Tokens live in httpOnly cookies **scoped to `/<slug>`**, so one app's session can't be replayed on another under the shared host.

Runs on port **3050** (`pnpm --filter @rekey.dev/portal dev`); needs only `REKEY_URL` (+ `PORTAL_BASE_URL` for checkout return links). The API must have `PUBLIC_PORTAL_URL` set to the same origin as `PORTAL_BASE_URL`, or it treats the deployment as running no hosted portal and refuses portal password resets.

Upgrading from 2.3: [migrating-to-2.4.md](migrating-to-2.4.md) covers the settings this page depends on, the one migration, and what changes for your customers when the new pages appear.

**Roadmap:** invoice PDFs, payment-method update, changing plan in place, and passkey management.

## Self-hosting

`apps/portal` is the thing you deploy. It is multi-app by construction and holds no per-app secret, so self-hosting it is the same app described here pointed at your own API — see [Environment](#environment) and [Run with Docker Compose](#run-with-docker-compose) below.

There used to be a single-app V1 reference at `examples/portal` that took one Application **secret key** per deployment. The `examples/` apps were removed in #261 pending a rebuilt set, and that model is not the one to copy anyway: a per-deployment secret key is exactly what V2 exists to avoid.

## Environment

`apps/portal` reads two required variables (`apps/portal/src/lib/env.ts`) and one optional one. There is deliberately no per-app secret and no per-app display name, because both come from `GET /api/v1/portal/config/:slug` at request time. That is what lets one deployment serve every app.

| Variable | Required | Meaning |
|---|---|---|
| `REKEY_URL` | yes | Base URL of the Rekey API (e.g. `https://api.your-deployment.com`) |
| `PORTAL_BASE_URL` | **in production, yes** | Public URL of the portal itself; used for checkout success/cancel return URLs and password-reset link targets. Outside production it defaults to `http://localhost:3050`; under `NODE_ENV=production` an unset value **throws at first use** rather than defaulting, because a localhost return URL strands customers after payment. |
| `PUBLIC_PORTAL_URL` (on the **API**) | yes | Not a portal variable: the API's copy of the portal's public URL. It must be the same origin as `PORTAL_BASE_URL`. Unset means the API treats the deployment as running no hosted portal: the panel shows no portal URL, checkout readiness reports no hosted portal, and portal password resets are refused with `AUTH_URL_NOT_ALLOWED`. The root `.env.example` sets both to `http://localhost:3050`. |
| `PORTAL_TRUSTED_PROXY_HOPS` | no | How many proxies you run in front of the portal (Traefik alone = `1`). The portal then forwards the visitor's address (the entry that many from the right of `X-Forwarded-For`) on its server-side API calls, so the API's per-IP limits count each visitor rather than the portal. Unset forwards nothing, which is right when nothing sits in front: any header the portal received then came from the client. `docker-compose.prod.yml` sets `1`. Believed only together with `PORTAL_PROXY_SECRET`. See [rate-limits.md](rate-limits.md). |
| `PORTAL_PROXY_SECRET` | with the above | Your proxy sends it as `X-Rekey-Proxy-Secret` on every request (a Traefik header middleware in the compose files). The portal believes `X-Forwarded-For` only on a request that carries it, so a caller that reaches the portal around the proxy cannot choose the forwarded address. |
| `INTERNAL_CALLER_SECRET` | yes, set on the API too | Sent to the API as `X-Rekey-Caller-Secret` on every server-side call; must equal the API's value. It does two things. When the portal calls the API's public origin, it is how the API tells the portal's calls from anyone else's through the same edge (without it every visitor counts as the portal's outgoing address). And on any path, it is what makes the API believe the visitor's User-Agent and country the portal forwards on a sign-in, so the session records the visitor's browser and platform instead of the portal's own `node` and `server`. Also required for an Application with `authConfig.deviceBinding: 'required'`: with the secret the API signs the customer in to the portal with a session that holds no device slot, and without it every portal sign-in for that Application is refused with `DEVICE_FINGERPRINT_REQUIRED`, which the sign-in page explains as "this account signs in through the app". Required by `docker-compose.prod.yml`. |
| `PORTAL_EXTRA_HOST_RULES` (`docker-compose.prod.yml` only) | no | Routes Applications' verified custom domains to the portal, and gets Traefik a certificate for each. Traefik rule text that follows the portal's own `Host()`, such as `` || Host(`billing.yourapp.com`) || Host(`account.other.com`) ``. Unset routes only `PORTAL_HOST`. See [Custom domain](#custom-domain). |

```bash
# local dev
cd apps/portal
REKEY_URL=http://localhost:3030 pnpm dev
# → http://localhost:3050/<slug>
```

There is no `REKEY_SECRET_KEY` / `PORTAL_APP_NAME` here. Those belonged to the removed single-app V1 reference; V2 resolves both per request from `GET /api/v1/portal/config/:slug`.

## Run with Docker Compose

The portal is containerized like the panel: a `portal-runtime` stage in the
root `Dockerfile` (Next standalone output, runs as the unprivileged `node`
user, port **3050**) plus a `portal` service in both compose files.

**Local stack** (`docker-compose.yml`, behind the `full` profile like
api/panel):

```bash
docker compose --profile full up --build portal
# → http://localhost:3050/<slug>  (talks to the api service at http://api:3030)
```

**Production** (`docker-compose.prod.yml`, Dokploy/Traefik): the `portal`
service is routed at `portal.rekey.dev`, `restart: unless-stopped`,
`depends_on: api`, and reaches the API over the private `rekey-edge` network
(`REKEY_URL=http://rekey-api-edge:3030`) from a fixed address the API trusts
to forward visitor IPs. `PORTAL_BASE_URL` is preset to
`https://portal.rekey.dev`. Nothing else to configure — **one** deployment
serves every opted-in Application at `/<slug>`, which was the entire point of
V2; there is no per-Application service, hostname or secret to provision. Full
deploy steps: `DEPLOY.md` → "Customer portal".

## What end-users can do

The hosted portal is where an Application's customers manage their account: sign in or create an account, pay for and manage a subscription, look after their security settings, profile, licenses, devices and organization, and approve sign-in for a desktop app. It holds no per-application secret, so it only ever does what the Application's publishable key and the customer's own session allow.

- **Sign in** (`/<slug>/login`): the page offers what the Application allows, from the portal config's `auth` facts. With password sign-in on, email and password over `/api/v1/auth/*` with an httpOnly cookie session that refreshes itself through `/<slug>/session/refresh`. A wrong email and a wrong password share one message, so the page never says which accounts exist, and the typed address waits in a five-minute httpOnly cookie scoped to `/<slug>` so the form can offer it again without putting it in the URL; a lockout (`TOO_MANY_FAILED_ATTEMPTS`) or rate limit (`RATE_LIMITED`) tells the customer roughly how long to wait, from the API's `retryAfterSeconds`, and a service or setup failure says it is not a problem with their account.
- **Sign-in link** (`/<slug>/login`, then `/<slug>/sign-in-link`): with magic-link sign-in on, the customer asks for a link by email. When sign-up is open (`signupMode: public`), the form says the link signs you in and creates your account if you are new, and the page then says "We sent a sign-in link to that address." When sign-up is closed, the page says "If that address can sign in here, we sent it a link." Either way the message is the same whether or not the address has an account, unless the request was rate limited or the service failed. The link points at `<PORTAL_BASE_URL>/<slug>/sign-in-link?token=…`. That route spends nothing: it moves the token into a fifteen-minute httpOnly cookie scoped to `/<slug>` and redirects to a token-free page with a **Sign in** button, so a mail scanner that fetches the link cannot use it up, and the token never sits in a rendered page's URL or Referer. The button signs in exactly as a password does, including the MFA step. With neither method on and no social provider, the page says sign-in happens in the operator's application and shows the support link.
- **Social sign-in** (`/<slug>/login` and `/<slug>/sign-up`, then `/<slug>/oauth/callback`): one **Continue with …** button per provider in `GET /api/v1/auth/oauth/providers` that the operator offers in the portal (`hostedPortal: true`, off by default, see the operator note below), in the API's order and with its names. A button starts the sign-in on the portal server: it keeps a random `state` and the provider in a ten-minute httpOnly cookie scoped to `/<slug>`, and calls `POST /api/v1/auth/oauth/:provider/start` with that state and `redirectUri: <PORTAL_BASE_URL>/<slug>/oauth/callback`. The provider sends the browser back to that page with a one-time code. The page renders nothing: it refuses a state this browser did not start (and spends the cookie either way), then spends the code at `POST /api/v1/auth/oauth/:provider/callback` with the same `redirectUri`, the publishable key and the caller secret, so a device-bound Application gets a portal session. The session comes back in that response body and goes only into the session cookies, then sign-in finishes like any other, including the MFA step, required two-factor setup and the `return` page. A provider that did not confirm an address already in use (`OAUTH_EMAIL_NOT_VERIFIED`), shared no address (`OAUTH_NO_EMAIL`), a closed sign-up, a refused domain, a canceled consent screen and an expired attempt each have their own message naming the provider. There is no PKCE, because the API's end-user sign-in `start` and `callback` do not use it for any provider.
- **Create an account** (`/<slug>/sign-up`): offered only while the portal config's `auth.signup` is true (`signupMode: public`); otherwise the page redirects to sign in and sign-in shows no link to it. With password sign-in on, it asks for an email and a password (the minimum under the field, a show toggle) and calls `POST /api/v1/auth/sign-up` with `verifyUrl` set to `<PORTAL_BASE_URL>/<slug>/verify-email?token={token}`. When the Application requires a confirmed address, the API answers a new and a taken address alike (`EMAIL_NOT_VERIFIED`; the owner of a taken one is emailed instead), and the page shows "Check your inbox" with the resend control, never whether the address had an account. Otherwise the API returns a session, and sign-up finishes like any sign-in, including required two-factor setup and the `return` page. With confirmation off the API answers a taken address with `EMAIL_ALREADY_EXISTS`, and the page says "You already have an account. Sign in instead.": the API has already said it, so hiding it would protect nothing. A refused domain or throwaway address (`SIGNUP_EMAIL_DOMAIN_NOT_ALLOWED`), a short or breached password and a rate limit each have their own message, and the form keeps the address (in the same five-minute cookie sign-in uses) but not the password. With only sign-in links on, the page offers the emailed link, which creates the account when used. When the branding sets `termsUrl` or `privacyUrl`, a line under the button says that creating an account means agreeing to them; there is no checkbox, because the API records no consent. The only bot guard besides the API's sign-up limit (10 per Application and IP address) is a hidden field: a submission that fills it gets the "Check your inbox" page and the API is never called. Profile answers are not sent with sign-up: the route takes none, and asking for them afterwards cannot leave an account half made.
- **Profile questions** (`/<slug>/profile/complete`): when the Application's profile schema has required fields the customer may answer (`GET /api/v1/profile-schema`) and the signed-in customer's profile lacks any of them, the dashboard, plan and devices pages send them here first, on every request, after two-factor setup. Each field type gets its own labelled input (text, number, web address, date, a select for options, Yes and No for a yes/no field), required ones are marked, answers are checked on the portal server, and a refused answer is shown under its field with focus moved to the first. Saving calls `PATCH /api/v1/users/me/profile` and then `POST /api/v1/users/me/onboarding/complete`, then goes on to the page sign-in was headed for. Any call the API refuses with `PROFILE_INCOMPLETE` also comes here. When the schema cannot be read the customer goes on: an outage does not lock anyone out of their billing.
- **Email confirmation** (`/<slug>/login`, then `/<slug>/verify-email`): when the Application requires a confirmed address and sign-in is refused with `EMAIL_NOT_VERIFIED`, the page offers a new confirmation link for the address just typed. The answer is always the same "if that address needs confirming, we sent a new link" message, unless the request was rate limited or the service failed. The link points at `<PORTAL_BASE_URL>/<slug>/verify-email?token=…`, which works like the sign-in link: the route spends nothing, holds the token in an hour-long httpOnly cookie scoped to `/<slug>`, and redirects to `/<slug>/verify-email/confirm`, where a **Confirm email address** button spends it. Confirming does not sign the customer in (the API returns no session), so the page links to sign in. An expired, used or stale link says so and offers a new one.
- **MFA challenge** (`/<slug>/login?step=mfa`): an end-user enrolled in two-factor is asked for their authenticator or backup code after the password. The challenge token is held in a five-minute httpOnly cookie scoped to `/<slug>`, never in the URL, and is cleared on success, when the API says the challenge is dead, and on sign-out. Without it the page sends the customer back to sign in. A backup code that was already spent is named as such (`MFA_BACKUP_CODE_USED`), and the field takes letters, since backup codes contain them.
- **Required two-factor setup** (`/<slug>/two-factor/set-up`): when the Application sets `authConfig.mfa: 'required'`, a customer with no second factor still gets a session at sign-in (the API flags it with `mfaEnrollmentRequired`). Every sign-in path that reports it lands here instead of the dashboard, and the dashboard and plan pages send the customer back here for as long as `GET /api/v1/auth/mfa/status` reports the policy required and the customer not enrolled. The page explains why, then on **Start setup** shows a QR code and the setup key, asks for the current 6-digit code, and shows the ten backup codes once with an **I have saved these** button. The key and codes come back only in the response to that action, never in a URL or a redirect. Sign out stays in the header. The API itself refuses an unenrolled session everything but enrolment (`MFA_ENROLLMENT_REQUIRED`). When the status call fails the customer goes on to the page, and the first call that page makes is refused that way and sends them here instead of showing an error. Optional enrolment, and turning two-factor off, are on the security page.
- **Devices** (`/<slug>/devices`): shown when the portal config's `auth.devices` is true (`authConfig.deviceBinding: 'required'`). A desktop app that hits its device limit can open this page; a signed-out visit goes to `/<slug>/login?return=devices`, and every sign-in path (password, the MFA step, the emailed link and required two-factor setup) lands back here. `return` is a keyword, not a path: `devices`, or `plan:<planSlug>` (a signed-out visit to a plan's page returns there; the slug must match the API's plan slug rule). Any other value is ignored. It is carried from the sign-in form to the end of sign-in in a fifteen-minute httpOnly cookie scoped to `/<slug>`, because the emailed link and two-factor setup leave the form. The page lists the customer's ACTIVE devices (`GET /api/v1/users/me/devices`) with their last use, and **Remove** releases one after a confirmation (`DELETE /api/v1/users/me/devices/:id`), which signs it out and frees its slot. The portal's own session holds no device, so there is no "this device". When the plan sets a `max_devices` limit (read from `GET /api/v1/billing/entitlements`, so only with billing on) the page counts devices against it, and at the limit links to the dashboard's plans. When the Application sets `deviceRelease: 'server_only'` the portal cannot know until a removal is refused with `DEVICE_SELF_RELEASE_DISABLED`; from then the page keeps the list and replaces **Remove** with a line asking the customer to contact support.
- **Security** (`/<slug>/security`, nav "Security"): a signed-out visit goes to `/<slug>/login`.
  - **Password**, when the portal config's `auth.password` is true: current and new password with show toggles and the minimum under the field (`POST /api/v1/auth/change-password`). The API revokes every session on a change, this one included, so the page says so before the customer submits and success lands on sign-in with "Password updated". The record's `hasPassword` decides which form shows. An account that never had a password (it signed up by link or with a provider) gets **Create a password** instead: **Email me a code** (`POST /api/v1/auth/email-code` with `purpose: set_password`), then the code and the new password (`POST /api/v1/auth/set-password`), which also ends every session. Without password sign-in the card says the account signs in by link.
  - **Two-factor**, unless `GET /api/v1/auth/mfa/status` reports the policy `off`: on or off and how many backup codes remain. Off shows the same setup steps as required setup. On shows **Turn off** behind a confirmation that takes a current or backup code (`POST /api/v1/auth/mfa/disable`; a browser caller must send one). When the policy is `required` the page says it cannot be turned off and shows no button. While two-factor is on, **Get new backup codes** takes a current authenticator code and shows ten new codes once (`POST /api/v1/auth/mfa/backup-codes`); the old ones stop working.
  - **Where you are signed in**: `GET /api/v1/auth/sessions`, each named by the browser and system in its User-Agent, with the date of its last token renewal and its IP address; **Sign out** revokes one (`DELETE /api/v1/auth/sessions/:id`) and **Sign out everywhere** revokes all (`POST /api/v1/auth/sign-out-everywhere`). The API marks the caller's own session with `current`, which the page labels "This session"; signing out of it clears the portal's cookies and goes to sign-in.
  - **Sign-in providers**: `GET /api/v1/auth/oauth/identities`, each with **Remove** (`DELETE /api/v1/auth/oauth/:provider`). `OAUTH_UNLINK_WOULD_LOCK_OUT` is explained as the only way the customer can sign in. Linking a provider is not offered here.
  - Passkeys are not managed here: enrolment binds to the operator's own domain.
- **Profile** (`/<slug>/profile`, nav "Profile"): a signed-out visit goes to `/<slug>/login`.
  - **Email address**, from `GET /api/v1/users/me`, with whether it is confirmed. **Change email** asks for the new address (`POST /api/v1/users/me/email`): a confirmation link goes to the new address and a notice to the current one, and the address changes only when the link is confirmed at `/<slug>/profile/email`, which ends every session.
  - **About you**: the operator's profile fields (`GET /api/v1/profile-schema`, only `writableBy: "user"` ones) with the customer's answers, one labelled input per field type (text, select, number, yes or no, web address, date). Saving checks each answer by the API's own rules and names a wrong one under its field, then sends only the answers that changed (`PATCH /api/v1/users/me/profile`); an emptied field clears its answer. The card is hidden when the application asks no questions. End users have no name field: an operator who wants one adds a profile field. The inputs are `components/profile-fields.tsx`, which renders no form of its own so other pages can reuse it.
  - **Delete account**: `DELETE /api/v1/users/me`, immediate and irreversible. The dialog says what is erased and what is kept, asks for the password when the account has one (a two-factor code works too; the API accepts either) and for `DELETE` typed out. An account with neither a password nor two-factor gets **Email me a code** (`POST /api/v1/auth/email-code` with `purpose: delete_account`) and sends the code as `emailCode`; without it the API answers `EMAIL_CODE_REQUIRED`. A subscription still billing through a provider is refused with `ACCOUNT_HAS_ACTIVE_SUBSCRIPTION`, which points at the Overview page; `authConfig.accountDeletion` other than `self_service` is refused with `ACCOUNT_SELF_DELETION_DISABLED`, which points at support. On success the portal clears its cookies and shows `/<slug>/goodbye`.
- **Licenses** (`/<slug>/licenses`): the customer's license keys from `GET /api/v1/users/me/licenses`, each with the start of its key (`keyPrefix`), plan, status, kind, seats, expiry and issue date. The API stores only a hash of each key, so the page says the full key was shown once when it was issued and cannot be shown again. Under each active license, its machines holding a seat (`GET /api/v1/users/me/licenses/:licenseId/activations`): the label or the start of the fingerprint, first and last use, and seats used of the total (or machines in use for a license without seats). **Remove** asks first, then frees the seat without the key (`DELETE .../activations/:activationId`). It shows on a personal license, and on one pooled to an organization only when the customer is an OWNER or ADMIN there (read from `GET /api/v1/users/me/organizations`, fetched only when such a license is listed). A revoked or expired license has no seat to give back, and the page says so.
- **Organization** (`/<slug>/organization`, nav "Organization" when `billingSubject` is `org`, when the portal config's `auth.organizations` is true (`authConfig.organizationsEnabled`: any customer may create one there), or when the session has an active organization. A member of an organization on an application with organizations switched off and no active organization still reaches the page by its URL; the layout reads nothing per page that says whether a customer belongs to one): a signed-out visit goes to `/<slug>/login`.
  - **Your organizations**: `GET /api/v1/users/me/organizations` with the customer's role in each. **Make active** calls `POST .../:id/switch` and **Use my personal account** calls `POST .../clear-active-organization`; both re-mint the session, and the new pair is written to the cookies the way a refresh writes it. The API keeps a portal session a portal session.
  - **Members** of the active organization (else the first one listed): email, role and join date. What the customer may do is decided by the `baseRole` tier the API returns for the customer and for each member, never the role name: an OWNER or ADMIN invites, an OWNER changes or removes anyone else, an ADMIN anyone else who is not on the OWNER tier, and the role picker (from `GET .../roles`) leaves out disabled roles and, for an ADMIN, OWNER-tier ones. Anyone but an OWNER can leave. Every refusal (`ORGANIZATION_LAST_OWNER`, `ORGANIZATION_ROLE_INSUFFICIENT` and the rest) still has its own copy.
  - **Invite**: `POST .../:id/invitations` with `inviteUrl` set to this portal's `/invitation-link?token={token}` on the host the inviter is using (the shared host plus the slug, or the verified custom domain). The API emails it in the Application's branding, and the page says "We emailed an invitation to <address>" with **Copy link** as a secondary action and **Revoke**. When the API reports `emailSent: false` the page shows the link, once, for the inviter to send.
  - **Pending invitations**, for an OWNER or ADMIN: `GET .../:id/invitations`, each with its role, who invited them and when it expires (or expired). **Revoke** asks first (`POST .../:id/invitations/:invId/revoke`). The API stores only a hash of each link, so the old link cannot be copied again: **Resend** (`POST .../:id/invitations/:invId/resend`) makes a fresh one and emails it like a new invitation, and the API revokes the old.
  - **Create an organization**: `POST /api/v1/users/me/organizations` with a slug made from the name; `ORGANIZATIONS_NOT_ENABLED` says the app does not allow it.
- **Accept an invitation** (`/<slug>/invitation-link`, then `/<slug>/invitation`): like the sign-in link, the landing route spends nothing and renders nothing; it holds the token in a day-long httpOnly cookie scoped to `/<slug>` and redirects to the token-free invitation page. Signed out, the page links to `/<slug>/login?return=invitation`, and sign-in comes back. Signed in, **Accept invitation** calls `POST /api/v1/auth/organizations/accept-invitation`. The API refuses a different signed-in address with `ORGANIZATION_INVITATION_EMAIL_MISMATCH`; the page says to sign in with the invited address and keeps the invitation. A used, revoked or expired one is dropped. Before any of that the page reads the invitation by its token (`POST /api/v1/auth/organizations/invitation-preview`, publishable key, no session) and says who invited them to which organization, as what role, which masked address it was sent to and when it expires; signed in as another address, it names the masked address to sign in with instead. A token the API answers `ORGANIZATION_INVITATION_UNAVAILABLE` for gets one line saying the invitation is no longer valid and no button; when the preview cannot be read at all the page falls back to the plain invitation.
- **Authorization for apps** (`/<slug>/authorize`): when the Application acts as an OpenID Connect provider or hosted MCP server (`oidcEnabled` or `mcpEnabled`) and has no `hostedAuthorizeUrl` of its own, the API's authorization endpoint sends the browser here instead of rendering its built-in password page. This is how a desktop app signs its user in: it opens the system browser at the authorization endpoint, and the user signs in with whatever the portal offers (password, emailed link, the code step, required two-factor setup, email confirmation). The URL carries only `?request=<id>`, an opaque id the API issued for the stored request; the route remembers it as the page sign-in returns to (`authorize:<id>`, in the same fifteen-minute httpOnly cookie) and goes on to `/<slug>/authorize/consent`. The consent page shows the Application's name, the client's own name labelled as the app requesting access (apps choose their names and nobody checks them), where the answer will be sent (the web host, `127.0.0.1:<port>` described as a program on this computer, or an app's own scheme), what each scope allows (an unknown scope is shown as its name), the signed-in email with **Not you? Use a different account** (signs out and comes back to this request), an account choice when an `mcp:account` grant could act for an organization, and **Allow** and **Cancel**. Consent is asked every time; nothing is remembered. Allow and Cancel are Server Actions that call the API from the portal server. A web redirect URI receives the browser directly; a loopback or custom-scheme one goes through `/<slug>/authorize/done`, which reads the redirect from a one-minute httpOnly cookie (never its own URL), opens it, says "You are signed in. You can return to <app> and close this tab.", keeps an **Open <app>** link to the same target in case the system did not open the app, and clears the cookie. An expired, used or unknown request says to start again from the app. On an Application that binds sign-in to a device (`deviceBinding: 'required'`) the portal's session holds no device slot and cannot approve another app: the page says "<App> signs in from the app itself, so it cannot approve <client> here." and offers only **Go back to <client>**, which sends the client `access_denied`.
- **Password reset** (`/<slug>/forgot-password`, then `/<slug>/reset-password`): request a reset email and set a new password from its link. The link points at `<PORTAL_BASE_URL>/<slug>/reset-password-link?token=…`, which the API accepts without the operator registering it, see below. Like the sign-in link, that route serves no page: it moves the token into an hour-long httpOnly cookie scoped to `/<slug>` and redirects to the token-free `/<slug>/reset-password` form, which states the minimum length under the field and spends the token on submit.
- **Dashboard** (`/<slug>`), one page once signed in:
  - **Subscription**: current plan, what this subscriber pays each period (the subscription's own price, which can differ from the plan's price today), status badge, and the renewal or end date. On an org-billed Application it shows the session's active organization, else the first team the user owns or admins; only an owner or admin (by tier) can buy or cancel there, and `BILLING_ORGANIZATION_REQUIRED` links to the organization page.
  - **Plans**: the active plan catalogue, each plan at the price the API resolved for this buyer (`plan.price.formatted`), with **Subscribe** (or **Buy** for a one-time plan) through hosted checkout (`billing.createCheckout`), and a "Pay with…" choice when more than one provider is on offer. When the price in the buyer's own currency cannot be charged and the default price is charged instead, the portal says so before they pay: "Prices in INR are not available yet. You will pay $19.00 (USD)." The plan's own page (`/<slug>/plans/<planSlug>`) also says how a subscription renews and how to cancel it, in the same words as checkout. A buyer who already holds a plan is told that this starts a separate subscription and leaves that plan in place: the API keeps one subscription per plan and checkout ends none. Activation lands via the provider webhook, as always: back from checkout, the dashboard re-reads itself every few seconds for up to a minute until no subscription is pending, says when it is active, and drops `?checkout=success` from the address so a reload does not repeat it.
  - **Cancel**: `POST /api/v1/billing/subscription/cancel`. An **ACTIVE** subscription with a known `currentPeriodEnd` is canceled **at period end**: the row stays ACTIVE with `cancelAt` set, and is terminated on the day by the provider's webhook, or, when there is no provider, by the API expiring it on the next read. PAST_DUE subscriptions, PENDING checkouts and ACTIVE rows with no period end flip to CANCELED right away. A subscription sold through an inbound-only provider shows "managed through your billing account" instead of a cancel button. A UI that has to describe the outcome before making the call can ask `cancelsAtPeriodEnd` from `@rekey.dev/shared-types`, the same predicate the API decides from.
  - **Billing history**: the caller's twelve most recent payments via `GET /api/v1/billing/payments` (strictly caller-scoped server-side), each amount written in its own currency and a partly refunded payment showing how much was refunded, linking to the provider receipt URL when the payment's metadata has one (`receiptUrl` / `receipt_url`, https only).
  - **Devices**: a link to the devices page, when the portal config's `auth.devices` is true.
  - **What your plan includes**: each feature and limit from `GET /api/v1/billing/entitlements`, as a label and a value (Included, Not included, a number or text). The `max_devices` limit links to the devices page when there is one. Hidden when the plan grants none.
  - **Usage this period**: each meter from `GET /api/v1/usage/remaining` that has a quota or recorded use, as "1,200 of 5,000 requests used" with a `role="meter"` bar and the date the period resets.
  - **Credits**: the balance from the entitlements read and the five latest entries of `GET /api/v1/credits/me/ledger`. Hidden while the balance is zero and the ledger empty.
  - **Licenses**: a link to `/<slug>/licenses` when `GET /api/v1/users/me/licenses` returns one. The nav has no Licenses entry, because nothing in the portal config says whether a customer holds a license and the header must not make that call on every page.
  - **Free plan and trials**: a free plan checkout cannot sell gets **Start**, which calls `POST /api/v1/billing/subscribe` (no payment provider involved). That route activates the application's nominated free plan (`billingConfig.defaultPlanSlug`), which the plan list names as `defaultPlanSlug`, so **Start** appears on that plan and on no other free plan, and nowhere when the application has none. A customer already subscribed to it sees it marked **Current** with no **Start**; one who only gets it at read time (no subscription yet) still sees **Start**, which is idempotent. A plan to buy says "Includes a 14-day free trial." only when `GET /api/v1/billing/trial-eligibility` answers that this buyer is eligible, and says when the trial is running or already used.
  - **Header**: the application name (and logo) links back to the dashboard. A signed-in customer also sees the account sections (Overview, Devices when `auth.devices` is true, Security, Profile, and Organization when the application bills or allows organizations or one is active; the list is `PORTAL_NAV` in `apps/portal/src/lib/portal-nav.ts`), their email address and **Sign out**. The footer links the operator's support contact, terms (`termsUrl`) and privacy policy (`privacyUrl`) when the branding sets them.
- **Hosted checkout** (`/<slug>/checkout/<token>`): the checkout page a `billing.createCheckout` link opens. It does not need the portal switched on, and it is covered in [billing.md](billing.md).

## Notes for operators

- **Email transport**: password reset, sign-in links and email confirmation from the portal need the Application to have an email transport (Panel → Application → Email). Without one the links cannot be delivered, and the portal deliberately does **not** show the raw token (anyone could type any email).
- **Reset link destination**: nothing to register. While the portal is on, the API treats this Application's own portal pages as an allowed destination for emailed token links: `<PUBLIC_PORTAL_URL>/<slug>/...` on the shared host, and the whole origin of a verified custom domain. It is scoped to the slug, so one Application cannot mail a token into another Application's pages on the same host, and it stops when the portal is turned off. The portal's `PORTAL_BASE_URL` and the API's `PUBLIC_PORTAL_URL` must name the same origin, or resets are refused with `AUTH_URL_NOT_ALLOWED`.
- **Social sign-in in the portal is opt-in per provider**: the provider sends the browser back to the portal, not to Rekey's API and not to your app, so first add `<PUBLIC_PORTAL_URL>/<slug>/oauth/callback` (and `https://<custom domain>/oauth/callback` once a verified custom domain is served) as an authorized redirect URI in the provider's console, alongside your own app's. Then tick **Offer in the hosted portal** on that provider (Panel → Application → Authentication → Sign-in providers; the box and the exact URLs, with copy buttons, show while the hosted portal is on), or send `hostedPortal: true` to `PUT /api/v1/tenant/applications/:id/oauth-config/:provider`. Every provider starts off: the portal shows no button for it, and the API refuses the portal page for it with `OAUTH_PROVIDER_NOT_IN_PORTAL`. The **Redirect URI** field on the provider's entry stays your own app's callback, which is still the right value for your app; the portal names its page per request. A GitHub OAuth App takes a single callback URL on one host, and Rekey holds one app per provider, so an OAuth App that already calls back to your app cannot serve the portal; keep GitHub off in the portal in that case.
- **Org-billed Applications**: if `billingConfig.billingSubject === 'org'`, checkout bills the active organization (or the first the customer owns or admins). With none, checkout fails with `BILLING_ORGANIZATION_REQUIRED`, and the portal links to its organization page.
- **Scopes** — nothing to configure. The portal presents the Application's publishable key plus the end-user's own token, and `requireScope` does not apply to a publishable caller; every self-service route scopes server-side to `request.endUser.id`.
- **Branding**: the theme is neutral on purpose (no Rekey branding). Design tokens live in `apps/portal/src/app/(portal)/globals.css`, with the values the checkout page shares (text, muted text, border, radius, focus outline) in `apps/portal/src/app/shared-tokens.css`. The operator's primary, background and surface colours from the portal branding replace the defaults when the portal's text stays readable on them. The portal follows the visitor's dark mode only when the operator set none of those three colours, since a brand colour was chosen for a light page.

## Custom domain

An Application can serve its portal on its own hostname, such as `billing.yourapp.com`, as well as on `<PUBLIC_PORTAL_URL>/<slug>`. Once the domain is verified and the request reaches the portal, the portal serves the Application there with no slug in its URLs: `https://billing.yourapp.com/plans` is the page `<PUBLIC_PORTAL_URL>/<slug>/plans` serves on the shared host.

**Operator steps** (Panel → Application → Billing → Portal → Custom domain):

1. Enter the hostname and save. It must be a bare hostname: no scheme, path, port or wildcard, and not an IP address. It is stored lower-case, without a trailing dot, and an internationalised name is stored in its `xn--` form. The hosts of this deployment's own API, panel and portal are refused.
2. Point the hostname at the portal with a CNAME to the host of `PUBLIC_PORTAL_URL`. The panel shows the target.
3. Publish the TXT record the panel shows, named `_rekey-portal.<hostname>`, with a value that starts `rekey-portal-verification=`.
4. Make the host reachable over HTTPS. On a self-hosted deployment, your reverse proxy must route the host to the portal service and hold a certificate for it (below). On a hosted deployment, it depends on what that deployment supports. Until it is verified, the portal answers that host with an empty 404, so opening `https://<hostname>/` and getting that 404 over a valid certificate shows the routing works.
5. Click **Verify domain**. Verifying switches the links in your emails, the authorization page and checkout returns to this domain straight away, so do it only after step 4. If the record has not reached the resolver yet, wait a few minutes and try again. A failure names the record expected and what was found. Clearing the hostname switches the links back to the shared address.

The same steps work from the API: `PATCH /api/v1/tenant/applications/:id/portal` with `{ "portalDomain": "billing.yourapp.com" }`, read `portalDomainTxtRecord` from `GET /api/v1/tenant/applications/:id`, then `POST /api/v1/tenant/applications/:id/portal/domain/verify`.

**What verification proves.** That whoever controls DNS for the hostname published a value only this Application is given. The value is derived from the API's `JWT_SECRET`, the Application id and the hostname, so a record published for one Application or hostname never verifies another. Changing `JWT_SECRET` changes every value, so every verified domain lapses (below) until its record is published again.

**What a verified domain gets.** Only a verified domain is used: `GET /api/v1/portal/config?host=<hostname>` finds the Application by it (exact match only), its origin is allowed for browser calls with the publishable key, emailed sign-in, verification and reset links may point anywhere on it, checkout return URLs on it raise no warning, and links Rekey builds (the payment-failed email, the checkout page's manage link) use `https://<hostname>` with no slug path. The checkout page itself stays at `<PUBLIC_PORTAL_URL>/<slug>/checkout/<token>`.

**How the portal answers on it.** For a request whose host is not the host of `PORTAL_BASE_URL`, the portal asks the API which Application holds that host as a verified domain, and remembers the answer for a minute (per portal process, either way). So a domain that lapses or is removed stops being served within a minute, and a domain verified after someone visited it is served within a minute. A host no Application holds verified gets an empty 404. An IP address or a single-label name (such as `localhost`) is served as the shared host, as before. On the domain:

- `/<page>` serves the Application's `/<slug>/<page>`. A link or redirect to `/<slug>/<page>` is answered with a permanent redirect to `/<page>`.
- Checkout goes to `<PUBLIC_PORTAL_URL>/<slug>/checkout/<token>` on the shared host, the only place the API accepts it.
- The portal's cookies are scoped to `/` rather than `/<slug>`: the domain belongs to one Application. A session on the domain and one on the shared host are separate sign-ins.
- Emailed sign-in, confirmation and reset links, and checkout return URLs, point at `https://<domain>/...`, and the portal's calls with the publishable key carry `Origin: https://<domain>`. Always `https`, because that is the only origin the API allows for the domain. Nothing switches this to `http`, in development either. To try a domain locally, set `portalDomain` and `portalDomainVerifiedAt` on the Application in your local database (a name such as `billing.localhost` resolves to your machine), set `PORTAL_BASE_URL` to the shared host, and browse to `http://billing.localhost:3050`; emailed links still say `https://billing.localhost`, so open them by hand on the http address.
- When the API gives no answer, the portal answers 503 with `Retry-After`. It also caps how many hosts it does not already know it will look up (30 per 10 seconds per process), so a flood of made-up hosts cannot become a flood of API calls; past the cap, a domain the process has not looked up yet gets the same 503 until the window passes.

**What the reverse proxy must do.** Route the domain to the portal, terminate TLS for it, and pass the visitor's host on unchanged: either as `Host`, or as `X-Forwarded-Host` on a request that also carries `X-Rekey-Proxy-Secret` equal to `PORTAL_PROXY_SECRET`. The portal believes `X-Forwarded-Host` only with that secret, so a request that reaches the portal around the proxy cannot pick an Application with it. Next.js checks a Server Action's `Origin` against `X-Forwarded-Host`, or `Host` when there is none, so whichever the proxy sends must be the domain the browser used. With `docker-compose.prod.yml`, Traefik does all of this once you list the domains in `PORTAL_EXTRA_HOST_RULES` (see the table above): it passes `Host` unchanged, sets `X-Forwarded-Host`, adds the proxy secret, and gets a certificate for each listed host.

**Who holds a hostname.** Several Applications may claim one hostname, but only one may hold it verified. Whoever verifies first holds it; a claim alone blocks nobody. Once a hostname is verified, another Application can neither verify it nor save it.

**Lapse.** The API looks up the TXT record of every verified domain again about every six hours. After three lookups in a row that find no matching record, which takes twelve hours or more from the moment the record is removed, the domain is no longer verified: it stops being honoured at once (the browser-origin allowlist on other API processes catches up within 30 seconds), the panel shows "Verification lapsed", and an `app.portal_domain_lapsed` security event is recorded. A lookup that fails because DNS did not answer does not count. To restore the domain, publish the record again and verify. Saving a different hostname also clears verification. The record's value never changes, so whoever controls the hostname's DNS later can keep it verified: clear the hostname in the panel before you give a domain up.

## API surface added for the portal

The authorization page uses three endpoints of the authorization server (`apps/api/src/modules/mcp/`), covered by `apps/api/test/portal-authorization-page.test.ts`. The portal names the stored request by `request_id` and nothing else, so it can only finish a request that came through the authorization endpoint:

- `POST /api/v1/mcp/:slug/oauth/authorize/preview` with `{ "request_id" }`: what the consent page shows. Needs the publishable key, the end-user JWT and `X-Rekey-Caller-Secret`.
- `POST /api/v1/mcp/:slug/oauth/authorize/grant` with `{ "request_id", "organization_id"? }`: spends the request and answers `{ redirect_to, expires_in }`, the client's redirect URI with `code` and `state`. Same credentials.
- `POST /api/v1/mcp/:slug/oauth/authorize/deny` with `{ "request_id" }`: spends the request and answers `{ redirect_to }` with `error=access_denied` and `state`. The publishable key and the caller secret; no end-user token, since it grants nothing.

A publishable key without the caller secret is refused (`403 SESSION_HANDOFF_FORBIDDEN`) on all three: the key and a user's token both reach browsers, and without the secret any script holding them could approve a client for the user. A hosted-portal session on an Application that binds sign-in to a device is refused by preview and grant with `403 AUTHORIZATION_NEEDS_DEVICE_SESSION`; deny still works. A user who still has to set up required two-factor is refused with `MFA_ENROLLMENT_REQUIRED` and sent to the setup page, which returns to the request.

The two billing endpoints live in the existing public billing module (`apps/api/src/modules/billing/billing.routes.ts`), take an Application **publishable or secret** key **and** the end-user JWT (`X-Rekey-User-Token`), and are covered by `apps/api/test/billing-portal.test.ts`:

- `GET /api/v1/billing/payments?limit=&offset=` — the caller's own payments, newest first (default 50, max 100), as `{items, page}` where `page` is `{total, limit, offset, hasMore}`. Projection only: no provider correlation ids, no raw metadata; `receiptUrl` is extracted server-side and https-filtered.
- `POST /api/v1/billing/subscription/cancel` — body `{ "atPeriodEnd"?: boolean }` (default true). Idempotent for an already-scheduled cancel; emits the `subscription.canceled` outbound webhook event on immediate/local cancellation (the at-period-end path emits when the provider webhook actually terminates the sub).
